# Rule Maintenance Manual

## 목적

운영 규칙을 수정할 때 한 문제를 고치면서 다른 Manual·Contract·Template에 모순이나 누락을 만들지 않도록 영향도 확인과 자체 리뷰를 강제한다.

## MUST — 수정 전

1. 변경 목적과 현재 문제를 한 문장으로 정의한다.
2. 변경 대상이 Contract, Manual, Index, Template 중 어디에 속하는지 판정한다.
3. 영향받을 Canonical 정의와 연결된 문서를 식별한다.

## CHECK — 백업 필요성

사용자가 현재 수정 전에 백업을 명시적으로 요구했거나 프로젝트의 별도 안전 정책이 백업을 요구하면 수정 전에 현재 기준점을 보존한다. 일회성 백업 요구를 모든 규칙 변경에 대한 영구 Branch 종류나 의무로 자동 승격하지 않는다.

## MUST — 수정 원칙

공통 정의는 Contract 한 곳에서 수정하고, Manual은 행동 절차만 수정하며, Index는 라우팅만 수정하고, Template은 Canonical 필드를 구현하는 골격으로 유지한다. 설명을 명확하게 만들 수 있는 문제를 해결하기 위해 새로운 State·Role·Code를 추가하지 않으며, 새 형식 값은 실제 라우팅이나 무결성에 반드시 필요하다는 근거가 있을 때만 제안한다.

## MUST — 자체 리뷰

변경 후 다음을 모두 확인한다.

- 같은 용어가 다른 의미로 중복 정의되지 않았는가.
- MUST/CHECK/MAY 강제성이 조건과 일치하는가.
- 각 Manual에 필요한 진입 조건과 완료 조건이 있는가.
- Work 상태와 Role 권한이 충돌하지 않는가.
- Template의 필드가 Contract 및 Manual과 일치하는가.
- Router와 Index가 새 문서로 연결되는가.
- 존재하지 않는 경로나 필드를 참조하지 않는가.
- 특정 저장소 이름에 불필요하게 의존하는 문장이 없는가.
- Reference를 프로젝트 Canonical로 오해하게 하는 문장이 없는가.
- 사용자 종료 Gate를 우회하는 경로가 없는가.
- 같은 사실을 두 Projection이 독립적으로 소유하지 않는가.

## CHECK — 기존 조건으로 완성 불가

기존 Canonical 규칙끼리 충돌하여 어느 쪽을 바꾸지 않고는 일관된 규칙을 만들 수 없으면 임의로 한쪽을 폐기하지 않고 충돌·영향도·선택지를 사용자에게 보고하여 협의를 요청한다.
